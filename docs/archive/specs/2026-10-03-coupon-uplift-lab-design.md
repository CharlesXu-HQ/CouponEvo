# 站内优惠券 Uplift 实验项目设计

状态：供审阅。本文定义第一版的范围和接口；实际 dataset 的字段映射在接入时填写。

## 目标

基于一份固定的随机对照 dataset，让 Agent 修改 uplift 算法与发券策略代码、运行可重复的离线实验。业务希望比较两类决策：

1. 在预算内，增加尽可能多的活跃用户。
2. 在同一预算内，增加尽可能多的净收益。

第一版只研究“不发券”和“一种固定优惠券”。具体能评估哪项目标由当前 dataset 的字段决定：`visit`/`click`/`conversion` 不能自动当作 App 活跃，销售额不能自动当作毛利，假设的固定发券费用不能当作实际核销券成本。报告必须使用数据实际支持的指标名称。全量字段齐备时，净收益定义为增量毛利减增量券成本；毛利口径必须说明是否已扣券成本，避免重复扣减。

## 设计选择

新项目借鉴 LegoFlow 的分阶段检查、运行产物和 Agent 协调方式。算法训练和评测由确定性脚本执行；Agent 可以修改候选算法及策略实现，不能修改已冻结的 dataset、数据切分和评测定义。运行记录先保存在本地产物目录。MLflow 可在需要多人共享实验界面时接入，不作为第一版依赖。

## 数据契约

项目读取已存在的 dataset，不负责收集数据。成熟公开数据集的共同核心是干预分组、至少一个事后结果和干预前特征，例如 [MT-LIFT](https://github.com/MTDJDSP/MT-LIFT) 的 `treatment/click/conversion/f0...f98`、[Criteo Uplift](https://huggingface.co/datasets/criteo/criteo-uplift) 的 `treatment/visit/conversion/f0...f11`、[Hillstrom](https://blog.minethatdata.com/2008/03/minethatdata-e-mail-analytics-and-data.html) 的 `segment/visit/conversion/spend`，以及 [Lenta](https://www.uplift-modeling.com/en/latest/api/datasets/fetch_lenta.html) 的 `group/response_att`（到店）。这些数据并不统一提供成本或金额，因此接入契约分为必需字段、可选结果和实验元数据。

| 逻辑字段 | 必需性与含义 |
| --- | --- |
| `assigned_treatment` | 必需。0 为对照，1 为被随机分配到干预组；不能用实际核销反推分组 |
| `primary_outcome` | 必需。至少一个事后结果，记录原始语义、单位和观察窗口，如 App 活跃、访问、点击或购买 |
| `features` | 必需。决策时可用的干预前特征；可以是匿名字段 |
| `unit_id` | 若源数据有用户/随机分组单位 ID，必须映射；若没有，生成稳定行 ID，并明确不能检查跨行同一用户 |
| `assignment_probability` | 优先使用原试验记录或方案中的分组概率；若能确认简单随机分组且公开样本未按组非均匀抽样，可由各组占比估计并标记来源。分层、非均匀随机或抽样机制无法恢复时，不能给出可靠的策略价值估计 |
| `active_outcome` | 可选。只有标签定义与观察窗口符合业务促活时才映射；访问或点击可单列为代理结果 |
| `monetary_outcome` | 可选。明确 `revenue` 或 `gross_margin`，并记录币种、观察窗口、退款处理及是否已扣券成本 |
| `coupon_cost` | 可选。若有，记录逐用户实际成本及其口径，例如核销成本；不能把券面额或核销标志直接当成实际成本 |

原始列名通过 dataset manifest 映射到逻辑字段；manifest 同时记录结果语义、分组设计、概率来源、成本口径和预算口径。检查阶段验证字段、分组比例、缺失值、重复单位（若有 ID）、时间先后和特征可用性。训练、验证、最终测试三份切分写入冻结的 split manifest；有用户 ID 时按用户切分，没有时按行切分并在报告标注无法排除重复用户泄漏。同一 dataset 版本的所有候选算法共用切分。

## 目标可用性与预算口径

| 当前 dataset 能提供 | 可报告的效果 | 可用预算 |
| --- | --- | --- |
| 只有访问/点击/转化等二元结果 | 相应结果的 uplift；只有符合活跃定义的标签才报告「增量活跃」 | 若无成本，仅限发券人数/比例 |
| 活跃结果 + 实际券成本 | 固定预期券成本预算下的增量活跃 | 根据处理组观测成本估计预期成本，同时报告离线估计区间 |
| 收入 + 实际券成本 | 增量收入减增量券成本，标为「增量净收入」；不是利润 | 同上 |
| 毛利 + 实际券成本 | 若毛利未扣券成本，可报告增量净收益 | 同上 |
| 只有收入或毛利，没有成本 | 增量收入或增量毛利；不得报告扣成本后的结果 | 发券人数/比例；若业务另给固定成本假设，可另列「假设成本」情景 |
| 只有实际成本，没有金额结果 | 成本约束下优化现有二元结果 | 预期实际成本 |

固定券的成本也可能仅有明确的「每发一张券成本」业务常数。这可以用于预算模拟，但需与逐用户核销成本分开标记。缺失活跃、金额或成本时，相应业务目标标记为「本 dataset 不可评估」，不补造真实标签。

## 运行流程

```text
固定 dataset + split manifest
  → 数据契约检查
  → 候选 uplift 模型训练
  → 为可评估目标生成预算内发券策略
  → 验证集离线评测
  → 实验报告与下一轮假设
  → 选定候选后一次性运行最终测试
```

候选算法的接口是：输入训练集与发券前特征，输出当前 dataset 中可用结果的处理效应估计；有实际成本时额外输出预期处理成本估计。策略实现依据可用估计与预算决定是否发券。第一版至少提供当前业务规则（若可复现）、随机发券和一个简单 uplift 模型作为对照；所有策略使用相同 dataset、切分、预算及评测器。每项业务目标只在所需字段齐备时生成对应策略。

评测器利用随机分配概率，估计策略相对“不发券”的可用结果增量及策略成本，并报告不确定性区间；不可用的指标不计算。Qini/AUUC 仅用于诊断 uplift 排序；最终比较使用指定预算下的数据支持的策略效果。验证集结果可供 Agent 反复分析，最终测试集只用于选定方案后的确认。

## Agent 的权限和产物

Agent 可以修改候选模型、现有字段的发券前特征加工、训练方法及预算分配策略代码。每轮先运行静态检查和必要测试，再运行实验。Agent 不能改动数据版本、split manifest、目标指标计算或最终测试结果来提高分数。

每轮保存一份报告，包含实验假设、相对上一轮的代码变化、配置、dataset 与代码版本、可评估目标的策略指标、缺字段而不可评估的目标、与基线的差值及下一步判断。若 Agent 认为 dataset 缺少关键画像，在报告的“数据与特征缺口”章节记录建议字段、数据来源、发券前可用时间、现有分析证据、可能的数据泄漏风险及后续验证方法。Agent 只提交建议；human 决定是否发布新 dataset 版本。新版本发布后，基线与候选算法全部重新评测，跨版本成绩不直接比较。

## 第一版完成标准

1. 同一 dataset、切分、代码版本、配置和随机种子可以复跑出相同结果。
2. Agent 至少能完成一次“修改候选代码 → 检查 → 运行 → 分析报告”的完整循环，保留每轮代码与结果。
3. 对每份 dataset 自动判定目标可用性：字段齐备时比较增量活跃与净收益两种策略；字段不齐时只报告可识别结果，并说明预算口径及缺失项。可评估结果含不确定性区间。
4. 数据检查能拦截发券后的特征、无法确定随机分组概率来源的策略评估，以及有用户 ID 时跨切分的重复用户。
5. 报告能记录缺失特征建议，且当前实验不会隐式改动固定 dataset。

## 第一版以外

线上发券、实时决策、多种券面额、自动生成新 dataset、可视化服务与通用推荐/广告/搜索实验能力留待后续版本。
