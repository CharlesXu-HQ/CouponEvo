# 新 Harness 的 GPU 策略与执行验收

## 结论

主搜索完成了三轮自主实验，**主搜索执行闭环成立，优化策略与经验质量尚未通过验收**。Agent 确实根据历史结果切换了因果估计方法，但对首轮错误的预处理假设没有纠偏；后续实验的归因、异常判断和请求补数据的依据也存在问题。另一次经验复用搜索完成了一个候选的训练、评估与反思，最后因不合法的数据请求退出，未正常收尾。

这是新 Harness 的单版本行为验收。候选与基线的比较用于评价实验，未做 Harness 版本之间的对比。原始运行期间没有人工修改候选、插入纠正提示或替 Agent 决定下一步。独立审阅与预处理检查的结果没有反馈给这次搜索。

可核对的候选源码、研究提案、指标、反思、终止决定和 API 事件保存在[证据 JSON](harness-design-gpu-evidence-2026-10-05.json)。其中 Agent 原始提案和反思包含本报告指出的错误，不能当作已验证事实。

## 主要缺陷及证据

### 1. 未验证的编码假设被写成经验

Agent 断言 seed 的 `pd.get_dummies(train[features], dummy_na=True)` 将 V2 的约五万个取值展开为列，在验证集上全部变零。实际 V1–V7 全是数值类型，默认 `get_dummies` 保留这些数值列；在全部 50,720 个训练样本上检查，预处理前后均为 7 个特征列，V2 一直存在。

候选将低基数字段列入 `categorical`，却仍把数值 DataFrame 直接传给 `get_dummies`，没有显式指定需要编码的列。因此三轮 `_prepare_features` 输出也都是 7 列。seed 在线性求解前另加截距列，这与数值字段被独热编码是不同的操作。

第一轮实际主要变化是 ridge→MLP。技术经验却持续称其为“混合编码修正”；第三轮还建议恢复原始“V2 one-hot”做消融。指标上涨没有验证这个编码机制，错误事实已经进入可复用经验。

### 2. 优先级没有充分建立在可区分的诊断上

第二轮将新旧策略配对区间跨零解释为 T-learner 的 CATE 估计高方差。该区间衡量验证样本上的策略效应差值，并不是 CATE 拟合方差的诊断。提出 DR 探索可以有价值，但应明确这是待检验的机制猜想。

DR 同时引入交叉拟合、伪结果和 BCE 结果模型，且代码使用训练集的 `T.mean() = 0.5011435331`，与提案所称的已知随机概率 0.5 不一致。第三轮相对 T-learner 同时改变共享方式、显式交互和 MSE→BCE。这些是可比较的配置，但不足以独立归因于某一个结构机制。

设计要求先识别症状、选择能区分解释的实验。当前 `diagnose` 只让模型解释已有报告，不能实际执行新的预处理检查、残差切片或训练诊断。这限制了 Agent 对自身假设的验证能力。

### 3. 将离散指标打平解释为疑似评估异常

轮次 3 的候选、预测、策略哈希均与轮次 1 不同，但策略效应均值相同。Agent 因此怀疑评估或版本未更新。

对二元购买结果，随机概率 p=0.5 时，策略 IPW 均值为 `2 ×（选中处理组购买数 − 选中对照组购买数）/ N`。本例两者都是 `2 × 33 / 16907`。不同选择名单完全可能得到这个相同净计数。配对差值标准误大于零，也与不同用户的贡献正负抵消相符。

当前证据支持“验证集效应打平、排序指标下降”。哈希变化和均值相同本身不能证明评估异常。把这种现象优先送去版本排查，会消耗本可用于有效假设的预算。

### 4. 数据请求通过了数量门槛，未通过证据门槛

搜索结束时请求补充 V1–V7 的逐行测量时间戳和 treatment 分配时点。它引用了三种已执行机制，满足现有校验器的字段与试验数量要求。

然而唯一依据是三份报告都继承了相同的 `feature_timing=declared_only`。没有实测时点违例、没有确认泄漏，也没有一个试验特异的残差模式指向该缺口。这是一项合理的数据质量审计建议；本轮实验没有证明必须补完时间戳才能继续现有数据上的探索。

预算用尽应与数据阻断分别记录。当前终止 `data_request` 还会阻止 `finalize_search`，因此其语义错误存在实际流程后果。本次没有运行 finalize。若未来补充数据或改变筛选人群，需要生成新的数据版本，在该版本的同一切分上重跑基线与候选；不能把新旧人群的分数直接视为模型提升。

## GPU、协议与运行成本

所有基线及候选报告均为 `model_device=cuda`，CUDA 峰值分别为 35,390,976、76,288,512、76,313,088、76,809,216 字节。代码审阅确认 CUDA 张量求解或梯度训练、预测直接进入策略评分。交叉拟合 DR 的 nuisance 和最终 CATE 网络也在 GPU 上运行。数据预处理在 CPU 上完成。

四份报告的 dataset、manifest、split 指纹一致，验证集均为 16,907 人。完整源数据被固定分区使用；没有将源数据抽成小样本。每轮从 high 开始分析，风险标志触发 max，反思使用 high；触发链路成立，标志的语义精度仍有上述问题。

主搜索用时 654.846 秒，16 次 API 响应，服务商报告总 token 693,982，其中 prompt 572,313、completion 121,669。四次 GPU 评估约 97.5 秒，其余主要用于 Agent 调用。提案上下文从约 23.8 万字符增至 31.6 万字符；终止决定消耗四次提案调用。当前安全事件日志未记录每次提案被拒的完整原因，不能据此推断每一次重试的具体原因。

## 同任务经验复用

新搜索确实加载了主搜索的三条技术/业务经验。第一次选择 `diagnose`，诊断 API 超时；保留失败记录后以同一 journal、任务身份和代码恢复。恢复后 Agent 改为试验“软分群＋局部线性专家”的 treatment-effect 模型，明确引用了此前 T/DR/S 的结果，尝试了新的结构方向。该检查只读取验证集经验，不引入历史测试结果，也不比较 Harness 版本。

这次模型真实完成 CUDA 训练，峰值显存 92,696,064 字节，验证策略效应为 0.00402200，AUUC 为 0.00716639，Qini 为 0.00284865。相对 seed 的配对差值为 +0.00070977，95% 区间 [-0.00092972, 0.00234925]，仍跨零。代码存在一个新的输出语义错误：

```text
L0(x) = sum(gate_weight * baseline_logit)
d(x)  = sum(gate_weight * treatment_logit_effect)
L1(x) = L0(x) + d(x)

代码返回：d(x)
概率 uplift 应为：sigmoid(L1(x)) - sigmoid(L0(x))
```

模型用 `BCEWithLogitsLoss` 训练，却将 logit 差直接写入 `conversion_uplift`，还在说明中声称它等于概率差。由于用户的基准 logit 不同，这两种分数的排序可能改变。固定 evaluator 得到的策略效应仍是这套选人规则的验证估计，但不能用它证明声明的概率 uplift 模型已正确实现。

这次编码实际变为 18 列，原三轮为 7 列，研究提案却称保持相同编码。因此结构与编码的效果仍未分开。新提案还将“分群 gate 坍缩”列为否证条件，但没有向评价报告输出 gate 占用统计；这个条件实际上无法按现有报告验收。

该提案还把配对区间跨零写为“仅复现全局模型、没有可用新机制”的否证依据。跨零只能说明这批验证样本未提供充分的新旧差异证据，不能证明两个模型等效。探索阶段应区分未达到预期、证据不足和机制被否证；最终反思使用 `inconclusive` 比该预设否证叙事更谨慎。

需要同时记录检查有效的部分：high/max 分析和反思确实识别了 logit 与概率差的错配，并指出 gate 占用数据缺失，反思为 `inconclusive`，没有把点估计上涨写成最终提升。不过这份候选仍被搜索器列为 `eligible` 和当前验证集最佳。当前晋级门槛没有专门阻断这种预测语义问题，机制经验仍需明确标记“实现待修正”。本回合只有一个候选预算，未继续做修正实验。

预算结束后 Agent 连续四次返回 `request_data`，最终以 `ValueError: feature_request.basis must be experimental_evidence or domain_requirement` 退出。校验器拦住了不合法的请求，但搜索没有转换为正常的预算停止状态；未产生有效 `data_request` 或 `stop`。日志只能确认最后一次错误，不能推断前面每次请求失败的全部原因。

两次执行尝试合计进程运行时间 642.280 秒（不含中间人工恢复间隔），收到 9 次 API 响应，已返回的 usage 合计 519,101 token；另有一次超时请求未返回 usage，不能把这个总数当作完整计费量。恢复沿用既有 baseline 结果，没有重新执行已完成候选。

## 尚未覆盖的设计分支

- 本次 Agent 自行实现因果估计器和分群网络，没有选择 bundled `method_id`，因此没有触发本地模型源码读取。这个分支不能算本次 GPU 验证通过或失败。
- 没有验证 TensorFlow 模型执行、44 张卡的全部训练能力、序列/图输入、困难样本挖掘及所有训练方向。匿名静态优惠券数据不支持其中一些输入契约。
- 未触发显式业务规则允许的立即数据请求；该任务的 `domain_requirements` 为空。
- CouponEvo bridge 当前只保存 reflection 中的技术/业务经验，没有保存 standalone Harness 设计的 `future_feature_suggestions` 字段；非阻断建议路径尚有集成缺口。
- 单个数据集、单个种子的行为审计不能估计跨任务成功概率。本次也没有估计 Harness 相对于其他版本的收益。

## 应优先改进什么

1. **先核验事实和实现。** 在假设形成及经验落盘前提供可复查的执行证据：实际特征维数/编码结果、训练目标、propensity、fold 与预测来源；区分 logit、概率、概率差与策略评分。代码未实施的机制不得被总结为有效经验。
2. **让诊断真正能回答问题。** 基于现有训练/验证数据执行受控诊断，区分已测症状与尚未验证的解释；按信息价值、成本和可检验性安排下一轮，允许优先做消融或排错。
3. **核对实验差异与对照。** 保留网络、loss、预处理、采样及训练预算的实际差异；联动变化应明确标为配置探索，随后用消融缩小归因，不能自动晋级为单机制经验。
4. **修正统计解释和数据请求。** 提供策略估计量的含义、离散性、选择重叠及配对贡献诊断；将已知元数据疑虑、实验发现的特征缺口和预算停止区分开，实验型请求需要试验特异证据。终止请求反复不合法时，也应留下可解释的失败状态和下一步，而不是仅以异常退出。
5. **再降低探索开销。** 对静态知识和历史证据做按需读取，保留事实、失败条件和未解问题；优先纠正经验内容，再提高经验检索和复用效率。

上述是这次实跑识别出的修复顺序，不是给 Agent 规定必须逐项运行的模型清单。
