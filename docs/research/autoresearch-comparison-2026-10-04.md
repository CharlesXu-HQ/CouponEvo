# karpathy/autoresearch: transferable experiment-loop design

Reviewed 2026-10-04 against the upstream [README](https://github.com/karpathy/autoresearch/blob/master/README.md), [agent program](https://github.com/karpathy/autoresearch/blob/master/program.md), [training script](https://github.com/karpathy/autoresearch/blob/master/train.py), and [fixed preparation/evaluation module](https://github.com/karpathy/autoresearch/blob/master/prepare.py). Links target the upstream `master` branch and may change after this review.

## What the repository actually implements

- **An agent-directed experiment loop, not an in-process agent framework.** The human edits `program.md` and launches an external coding agent in the repository. The agent edits `train.py`, runs it, reads the metric, then keeps or discards the code change. The [README](https://github.com/karpathy/autoresearch/blob/master/README.md#how-it-works) names these three file roles; [program.md](https://github.com/karpathy/autoresearch/blob/master/program.md#the-experiment-loop) specifies the loop.
- **Narrow edit surface and stable measurement surface.** `train.py` contains the model, optimizer, and training loop; it is the only allowed agent edit. `prepare.py` holds the data loader, fixed constants, and `evaluate_bpb`, which the instructions forbid modifying. New dependencies and evaluation-harness edits are also forbidden. This is a [policy in `program.md`](https://github.com/karpathy/autoresearch/blob/master/program.md#experimentation), rather than a technical sandbox shown in the repository.
- **Comparable local experiment budget.** `prepare.py` fixes `TIME_BUDGET = 300` seconds, `MAX_SEQ_LEN`, a pinned validation shard, and `EVAL_TOKENS`; `train.py` counts steady training time after warmup and evaluates once at the end. The score is validation bits per byte, with lower better. Startup/compilation and final evaluation add to total wall time. See [constants and validation shard](https://github.com/karpathy/autoresearch/blob/master/prepare.py#L23-L39), [`evaluate_bpb`](https://github.com/karpathy/autoresearch/blob/master/prepare.py#L307-L332), and [training stop and final summary](https://github.com/karpathy/autoresearch/blob/master/train.py#L499-L582). The [README](https://github.com/karpathy/autoresearch/blob/master/README.md#design-choices) warns that fixed-time results depend on the hardware platform.
- **A baseline and an explicit keep/discard decision.** The first run establishes the baseline. For each proposal, the agent commits, redirects output to `run.log`, extracts `val_bpb` and peak VRAM, records one row in an untracked `results.tsv` (`commit`, score, memory, `keep`/`discard`/`crash`, description), and advances or resets the branch. Runs beyond ten minutes are treated as failures. See [baseline and logging](https://github.com/karpathy/autoresearch/blob/master/program.md#logging-results) and [loop/failure rules](https://github.com/karpathy/autoresearch/blob/master/program.md#the-experiment-loop).
- **Search decisions consider complexity as well as score.** The instructions ask the agent to prefer simpler code at equal quality and question small gains that require substantial complexity. This is an [instructional criterion](https://github.com/karpathy/autoresearch/blob/master/program.md#experimentation), not a measured penalty in `val_bpb`.

## Design ideas worth carrying into offline algorithm research

1. Keep the agent's editable candidate surface small and the evaluator, data split, metric definitions, and run budget outside that surface. Record which files were permitted for each run.
2. Establish a baseline before search. Give each proposal a code revision and a short hypothesis; save both successful and failed trials, including crashes and resource usage.
3. Make the acceptance rule machine-readable and separate the score used for search from final evidence. A validation improvement is a search signal; repeated use of the same validation set does not establish generalization.
4. Bound each trial's compute and fail fast on invalid runs. Use a stable budget and dataset identity so a score difference has an interpretable meaning.
5. Keep a simple experiment ledger that can be replayed. `autoresearch` uses Git commits plus TSV; a production-quality ledger could additionally persist dataset fingerprint, exact run configuration, uncertainty estimates, and final holdout outcome.

## Limits to copying the pattern directly

The upstream workflow optimizes **one scalar validation metric** for single-GPU language-model training. It does not provide a separate untouched test-set gate, statistical uncertainty for score differences, multiple business objectives, or causal policy evaluation in its published loop; these are visible gaps relative to a decision workflow, not defects in its stated scope. The repeated reuse of one validation shard creates a model-selection overfitting risk (inference from the [pinned shard](https://github.com/karpathy/autoresearch/blob/master/prepare.py#L33-L39) and [indefinite loop](https://github.com/karpathy/autoresearch/blob/master/program.md#the-experiment-loop)). The instructions leave `results.tsv` outside Git, and [`.gitignore`](https://github.com/karpathy/autoresearch/blob/master/.gitignore#L268-L270) ignores it; the run log is generated after the proposal commit. Thus a branch's code commits alone do not reconstruct every trial. Finally, its five-minute budget is for **training time**, and the [README](https://github.com/karpathy/autoresearch/blob/master/README.md#platform-support) currently centers on a single NVIDIA GPU; its exact budget and platform choices should not be copied as universal defaults.

## CouponEvo comparison (current main)

| Upstream principle | What CouponEvo already has | Useful next change |
| --- | --- | --- |
| Narrow edit surface, fixed evaluator | Candidate code is snapshotted and run in a restricted container; task identity includes dataset, manifest, objective, budget, seed, and evaluator hash ([search](../../src/couponevo/search.py), [sandbox](../../src/couponevo/sandbox.py)). | Keep this separation; do not collapse the framework into one editable file. |
| Human-authored research program | The search prompt is embedded in [`agent.py`](../../src/couponevo/agent.py); task JSON fixes inputs and objective but does not contain a versioned research brief. | Add a short, human-authored task brief for hypotheses, constraints, and stopping criteria; include its hash in the search identity. The Agent should still choose individual experiments. |
| Comparable compute budget | `max_steps` and a one-hour default per-candidate timeout bound attempts, while reports capture CUDA peak bytes ([search](../../src/couponevo/search.py), [report](../../src/couponevo/cli.py)). | Record actual candidate training/evaluation time and GPU memory, cap total GPU time, and fingerprint the mounted Python environment and GPU. Calibrate a suitable trial ceiling instead of copying 300 seconds. |
| Keep/discard with a compact ledger | `journal.json` stores hypotheses, snapshots, status, full reports, and the validation champion; the champion currently changes whenever the objective point estimate rises ([search](../../src/couponevo/search.py)). | Derive an experiment table from the journal with score delta, paired interval, runtime, complexity, and keep/discard reason. Retain failed and inferior snapshots for audit; no Git reset is needed. |
| One final claim | `finalize` already compares a frozen champion with the seed on an independent test set and computes paired bootstrap intervals ([search](../../src/couponevo/search.py)). | Preserve this stronger gate. Keep search bounded; an indefinite loop on one validation set would increase selection bias. |

The practical first increment is a **versioned task brief plus resource accounting**. Next, make the journal easy to review and state an acceptance rule that treats tiny validation gains with large complexity or compute cost as exploratory. Final uplift claims still require the untouched holdout; a validation confidence interval after adaptive search is not a final significance test.
